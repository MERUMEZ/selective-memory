# Как выпускать релиз

## Правило, из-за которого стоит быть внимательным

**Номер версии на PyPI сжигается навсегда.** Загрузили `0.1.0` — этот
номер занят, даже если релиз потом удалить. Ошиблись в чём угодно, хоть
в опечатке README, — выпускаете `0.1.1`.

**Переименовать проект нельзя.** Совсем. Можно только опубликовать под
новым именем, а старое оставить висеть с пометкой «не ставьте».

Поэтому: имя и публичный интерфейс должны устояться ДО первой
публикации на настоящий PyPI.

## Подготовка, один раз

**Выкладываем без токена вовсе.** Trusted Publishing: PyPI доверяет не
секрету, а конкретному workflow в конкретном репозитории, а проверка идёт
по OIDC-удостоверению, которое GitHub выдаёт запуску на несколько минут.
Отзывать нечего — секрета не существует ни в репозитории, ни в настройках,
ни на машине автора.

1. Завести учётную запись на https://pypi.org и на https://test.pypi.org
   — это **разные** сайты с разными паролями.
2. Включить двухфакторную аутентификацию (без неё PyPI не даст
   выкладывать).
3. На каждом из сайтов: Your projects → Publishing → Add a new pending
   publisher, и заполнить ровно так:

   | поле | значение |
   |---|---|
   | PyPI Project Name | `selective-memory` |
   | Owner | `MERUMEZ` |
   | Repository name | `selective-memory` |
   | Workflow name | `publish.yml` |
   | Environment name | `pypi` (на TestPyPI — `testpypi`) |

   «Pending publisher» — это правило для проекта, которого ещё нет: оно
   и создаст его при первой публикации.
4. В GitHub: Settings → Environments → создать `pypi` и `testpypi`.
   Имена обязаны совпасть с тем, что вписано на PyPI, иначе публикация
   получит отказ.

Дальше публикует [.github/workflows/publish.yml](.github/workflows/publish.yml):
ручной запуск метит в TestPyPI, а на боевой PyPI уходит только тег `v*`.

Токен по-прежнему возможен как запасной путь (`twine upload`), и если он
заведён, то выглядит как `pypi-AgEIcHlwaS5vcmc...` — хранить его в
репозитории нельзя ни в каком виде.

## Проверка перед каждым релизом

```bash
./venv/bin/python -m pytest tests/ -q                       # все тесты
./venv/bin/python tools/check_liveness.py                   # мёртвые механизмы
./venv/bin/python tools/compare_interference.py             # ниша: двойники
./venv/bin/python tools/compare_retention.py --balanced
./venv/bin/python tools/probe_semantic.py
```

`check_liveness.py` возвращает ненулевой код, когда механизм перестал
срабатывать ИЛИ продолжает срабатывать вхолостую. Случалось и то, и
другое, и ни разу это не поймал набор тестов; красный прогон — повод
задержать релиз.

**Проверяйте, что получает ЧУЖОЙ, а не своя машина.** Путь к
семантической модели по умолчанию указывал на диск автора: семантика
была выключена у всех пользователей, а 23 теста проходили на одном
компьютере. Поставьте колесо в чистое окружение и убедитесь, что
`stats().semantic` возвращает True с экстрой `[semantic]` и False без неё.

Если менялись числа — обновить их в README, AUDIT, COMMERCIAL и
докстрингах. `tests/test_readme_examples.py` проверяет примеры README
дословно, но таблицы с замерами он не сверяет: за них отвечает человек.

Поднять версию в **одном** месте — `__version__` в
[selectivemem/__init__.py](selectivemem/__init__.py). `pyproject.toml`
берёт номер оттуда, второй копии, которую надо не забыть, больше нет.
Строка обязана оставаться простым литералом: setuptools достаёт её
разбором синтаксиса, не импортируя пакет, и вычисляемое значение прочесть
не сможет. Оба свойства стережёт `tests/test_version.py`.

Правило простое:

| что изменилось | версия |
|---|---|
| исправление, поведение то же | `0.1.0` → `0.1.1` |
| новая возможность, старый код работает | `0.1.0` → `0.2.0` |
| сломали чужой код (переименовали метод, поле, пакет) | `0.x` → `1.0.0` |

## Сборка

```bash
rm -rf build dist
./venv/bin/python -m build
./venv/bin/python -m twine check dist/*
```

`twine check` должен сказать `PASSED` для обоих файлов.

## Сначала TestPyPI

Отдельный сервер. Имена и версии там **не резервируют** ничего на
настоящем PyPI, поэтому пробовать можно свободно.

GitHub → Actions → Publish → Run workflow, `target = testpypi`. Сборка,
тесты и `twine check` идут там же; выкладывает задание с правом подписи и
без единого секрета.

Запасной путь, если Actions недоступны:

```bash
export TWINE_USERNAME=__token__
export TWINE_PASSWORD=pypi-ВАШ_ТОКЕН_С_TEST_PYPI
./venv/bin/python -m twine upload --repository testpypi dist/*
```

**`403 Forbidden` почти всегда значит, что токен с другого сайта.**
pypi.org и test.pypi.org — разные системы с разными аккаунтами,
регистрация на одном не действует на другом. Проверять по порядку:
аккаунт на TestPyPI заведён, токен создан именно там, имя пользователя
ровно `__token__`, двухфакторная включена. Если существует `~/.pypirc`,
он побеждает переменные окружения. `--verbose` печатает настоящую причину
отказа от сервера.

**Чтобы посмотреть на страницу второй раз, нужен новый номер** — на
TestPyPI версия тоже сгорает. Брать не следующий настоящий номер, а
суффикс `.dev`:

```bash
sed -i 's/0\.1\.0/0.1.0.dev1/' selectivemem/__init__.py   # только для теста
```

Потом вернуть обратно, чтобы на боевой PyPI первый релиз уехал чистой
версией `0.1.0`.

Проверить, что получилось, в чистом окружении — **и не из каталога
репозитория**:

```bash
python -m venv /tmp/check && /tmp/check/bin/pip install \
  -i https://test.pypi.org/simple/ selective-memory
cd /tmp && /tmp/check/bin/python -c \
  "import selectivemem; print(selectivemem.__file__); print(selectivemem.__version__)"
```

**`cd /tmp` — это смысл команды, а не украшение.** Python кладёт рабочий
каталог в путь поиска, поэтому запуск рядом с папкой `selectivemem/`
импортирует исходник с диска вместо только что выложенного пакета. Это
уже случалось здесь: установка упала с «No matching distribution found»,
следующая же строка напечатала бодрый баннер, и при этом не было
установлено ничего.

Отличает одно от другого печать `__file__`. Она обязана указывать внутрь
`/tmp/check/lib/`, а не в репозиторий.

И глазами посмотреть страницу пакета: как отрисовался README, верны ли
ссылки, на месте ли лицензия.

## Потом настоящий PyPI

Здесь тег и есть публикация — отдельной команды выкладывания нет:

```bash
git tag -a v0.1.0 -m "Первый релиз"
git push origin v0.1.0
```

Тег `v*` запускает тот же workflow, и он идёт на боевой PyPI. Дальше
поставить оттуда в чистое окружение и убедиться, что всё работает.

Порядок именно такой — тег СОЗДАЁТ релиз, а не отмечает уже сделанный.
Иначе тег и выложенное расходятся, и потом не понять, из чего собран
пакет, который стоит у людей.

## Если что-то пошло не так

**Опечатка в README, метаданных, коде.** Выпускаете следующую версию.
Откатить нельзя.

**Выложили сломанное.** Пометить релиз как `yank` в веб-интерфейсе PyPI:
он останется доступен тем, кто его уже прибил в зависимостях, но новым
пользователям ставиться не будет. Это мягче удаления и не ломает чужие
сборки.

**Утёк токен.** Немедленно отозвать в настройках PyPI и создать новый.

**Нужно другое имя.** Опубликовать под новым, а у старого выпустить
последнюю версию, которая просто зависит от нового имени, и пометить
`yank`. Некрасиво, но работает.

## Что помнить про публичный интерфейс

После публикации ломающими изменениями становятся:

- переименование пакета `selectivemem` — ломает `import` у всех;
- переименование `Memory`, `observe`, `feedback`, `recall`,
  `context_for`, `forget`, `stats`;
- переименование полей `Observation` и `MemoryStats`;
- удаление поля из `MemorySettings` (добавлять новые — безопасно).

Менять умолчания настроек формально не ломает код, но меняет поведение
у всех разом. Такое стоит делать минорной версией и писать в
changelog — как было с порогом записи `0.35 → 0.25`.
